FreelanceHub

A MERN freelance marketplace for posting work, hiring talent, chatting, holding escrow (full job, milestones, or hourly hours), cancelling with refunds, and completing jobs with reviews. Tests, CI, Playwright, and Docker are part of the repo; Stripe, S3, Redis, and SMTP stay optional.

1. What this project is

FreelanceHub is a full-stack marketplace where clients post paid projects and freelancers bid. After a hire, the two parties chat, the freelancer submits work (optionally with files), the client can request revisions, cancel with an escrow refund, or approve. Simulated escrow is released on complete. Both sides can then leave a review. An admin account can inspect users, projects, contracts/escrow, reports, and an audit log.

The product is a classic MERN monolith (MongoDB, Express, React, Node.js). The demo holds money as one Payment per contract: hire creates held, complete or milestone/hour approval increments releasedAmount, cancel sets refunded. Stripe, object storage, Redis, and SMTP are env-optional. If they are unset, the same hire loop still works.

One-line summary. Post (fixed, milestones, or hourly) → propose (or rebid after withdraw) → hire (escrow hold) → chat → submit work → optional revision or cancel/refund → release (full, slice, or hours) → review.

2. Goals and non-goals

In scope

  • Email/password auth with httpOnly cookies, refresh tokens, and Bearer JWT
  • Email verify and password reset (JSON mailer or SMTP)
  • Project posting, URL-backed search, skill matching
  • One pending proposal per freelancer per project; rebid after withdraw
  • Hire, contract, escrow hold / release / refund
  • Fixed-price milestones with partial release, or hourly time against a budget cap
  • Invite-to-bid, chat attachments, saved searches, CSRF on cookie sessions
  • Deliverable uploads (disk or optional S3)
  • Project-scoped chat with join auth, multi-tab presence, typing
  • Saved items, shortlists, reports, verified-skill tags
  • Public client pages and richer freelancer portfolios
  • Admin analytics, contracts/escrow, audit log (no impersonation)
  • API tests, GitHub Actions CI, lint, Docker Compose

Out of scope (still)

  • Google / social login
  • LLM matching or generated cover letters
  • Native mobile apps
  • Multi-currency or a microservice split
  • Mandatory Stripe — it is a vertical slice behind env vars, not the default demo

4. System architecture

The browser never talks to MongoDB. It talks to Express over HTTP (JSON and multipart, cookies included) and to the same Node process over WebSockets. Access tokens travel as httpOnly cookie fh_access and/or Authorization: Bearer. Refresh uses cookie fh_refresh (or a JSON body). Socket.IO authenticates the handshake token or the access cookie.

On load, AuthContext calls GET /api/auth/me (cookies or stored Bearer token). A 401 triggers POST /api/auth/refresh; if that fails the UI signs out. Toasts replace alert() for proposal success and work actions.

6. Domain model

Collections are linked by ObjectIds. A project has at most one hired proposal. A contract is unique per project. A payment is unique per contract. Chat is unique per (project, unordered pair of users). Admin actions write AuditLog rows (blocks, report updates, skill verification). Impersonation is disabled.

8. Core hiring loop

This is the money path. Saved items, shortlists, reports, and presence sit on top of it.

Domain rules (enforced on the server)

  • Unique index on { projectId, freelancerId }. A second pending bid is 409. A withdrawn row is updated back to pending.
  • You cannot bid on your own project or on a non-open project. After a proposal exists, the project detail page shows status instead of a second form.
  • Accepting a bid rejects other pending bids, sets the project to in_progress, creates a contract (copying planned milestones, or a single “Full project” slice, or an hourly cap at budgetMax) and a held payment, and opens a conversation.
  • Chat requires a pending or accepted proposal. Socket conversation:join is participant-checked (join is not an open room id).
  • Only the hired freelancer can submit work. Only the client can request a revision or complete.
  • Either party (or admin) can cancel an active contract with a reason; held escrow becomes refunded and the project is cancelled.
  • Revision keeps status active, increments revisionCount, stores revisionNote, and clears workSubmittedAt.
  • Reviews are allowed only after completed, once per reviewer per contract.

9. Feature catalogue

9.1 Auth and profiles

Register is limited to freelancer or client. Passwords are hashed with bcrypt (cost 12). Login is rate-limited (40 / 15 minutes). Sessions set httpOnly cookies and return a Bearer token for sockets. POST /auth/refresh rotates refresh hashes. POST /auth/logout clears cookies even if the access token already expired. Email verification and password reset send mail through Nodemailer (JSON log in demo). SKIP_EMAIL_VERIFY=true (and NODE_ENV=test) skip the verify gate for local/seeded accounts.

Profiles store bio, location, avatar, freelancer skills/rate/portfolio images/availability, verified-skill tags (admin-set), or client company name. Public client pages list that company’s projects.

9.2 Projects and search

Browse keeps q, category, pricing type (fixed/hourly), due-soon, sort (newest / highest budget / due soonest), and page in the URL. Cards show Fixed price, Fixed · N milestones, or Hourly, plus pending bid counts and a relative due date (due in 3d / overdue 2d). Project detail lists the planned milestone table and a Similar open work strip from GET /projects/:id/similar (same category or overlapping skills). Clients see pending bid counts on My projects and can Duplicate any brief into a fresh open listing (new deadline, no hire). Talent browse keeps hourly-rate bounds in the URL. Matching score is skill overlap, capped at 100%.

9.3 Proposals and shortlist

Cover letter (counted out of 4000), bid amount, estimated days. The bid form warns when the amount is above budgetMax. Clients star pending proposals. The compare table can sort by shortlist, lowest bid, fastest delivery, or skill match, and flags over-budget rows.

9.4 Work, deliverables, revisions, disputes

Submit-work is multipart (PDF, ZIP, PNG, JPEG, WebP, 8 MB, up to 8 files). Files persist to disk or S3. The work card can Approve the whole job, release one milestone, approve hourly time against the escrow cap, Request revision, or Cancel & refund remaining escrow. Partial payouts live on Payment.releasedAmount — there is still one payment row per contract.

9.5 Saved items and saved searches

Freelancers bookmark projects; clients bookmark talent. /app/saved lists them. Named saved searches replay browse filters from the dashboard.

9.6 Messaging, unread, presence, typing

Unread count is threads whose latest message is not in readBy. Presence is a set of socket ids per user so a second tab does not kick the first offline. Chat notifications fire only if the other party is offline. Typing events stay inside the conversation room.

9.7 Notifications

Proposal received/accepted/rejected, work submitted, revision requested, contract completed, contract cancelled, review received, report updates. Alerts use a keyboard-focusable disclosure and aria-live unread counts. The inbox can Mark all read. Success toasts use aria-live="polite".

9.8 Reports and admin

Users report a user or project. Admins review or dismiss (audited). Admins block users (audited), verify skills (audited), and open contracts with escrow status. There is no impersonate control.

9.9 Desk extras (presentation pack)

Project edit, proposal compare table, notifications inbox with type filter, invite-to-bid, chat attachments, printable invoice at /app/work/:id/invoice, CSRF token cookie fh_csrf (skipped for Bearer and GET), and a Playwright hire-loop smoke in CI.

13. Security, auth, and validation

  • Passwords bcrypt-hashed; secret fields stripped from public user payloads.
  • Access cookie fh_access (httpOnly, SameSite lax, Secure in production) plus refresh cookie fh_refresh. Refresh token is stored hashed on the user.
  • Axios sends cookies and Bearer; 401 retries refresh once, then clears the UI session.
  • CORS origin is exactly CLIENT_URL with credentials. Socket.IO uses the same origin.
  • Zod on mutating routes. Multer rejects disallowed types. JSON body 1 MB. Auth rate limits skipped only in tests.
  • Request id header X-Request-Id on every response. Structured JSON logs.
  • CSRF: mutating cookie requests need header X-CSRF-Token matching cookie fh_csrf. Bearer JWT and GET/HEAD skip the check so API tests stay green.
Demo secrets. Rotate JWT_SECRET before any shared deploy. Disk server/uploads/ does not survive multiple API instances — set S3 for that. Payments are simulated unless Stripe env vars are set.

14. Tests, CI, and quality

cd server && npm test runs node:test + supertest against freelancehub_test (or MONGO_URI_TEST). The suite has 16 cases: register/login, public marketplace stats, unique proposal + rebid after withdraw, accept → contract + held payment, complete blocked without submission, revision clearing workSubmittedAt, cancel → refunded, myProposal on project detail, incremental milestone release, hourly time against the cap, chat attachment, CSRF skip for Bearer, invite-to-bid owner check, pricing-type list filter, budget sort, pending bid counts + similar projects, CSV ledger export, and project duplicate (owner-only).

cd client && npm test runs Vitest on format helpers (INR, pricing labels, relative times, due dates). cd client && npm run e2e is Playwright: a hire-loop smoke (register → post → bid → accept → submit) plus viva smokes (home copy, hourly filter, 404, Priya dashboard Scan MVP). GitHub Actions on main starts Mongo 7, runs server lint/test, then client lint/test/build, then Playwright.

17. Viva talking points

Memorise these answers. Examiners usually ask “why”, not “show me another screen”.

Likely questionWhat to say
Why a MERN monolith, not microservices?College demo has one team and one database. Splitting auth/projects/payments would add network hops without a production load. The API is still modular: models, controllers, routes, services.
Is the money real?No. Hire writes a Payment with status held. Complete or milestone/hour approval increments releasedAmount. Cancel sets refunded. Stripe is behind env vars for a later slice.
Why cookies and Bearer?The SPA sends httpOnly cookies so XSS cannot steal the access token. Socket.IO and Playwright still use Authorization: Bearer. CSRF is required only for cookie POSTs; Bearer skips it.
How do you stop double bids?Unique index on { projectId, freelancerId }. A second pending bid is 409. Withdraw sets withdrawn; the same row can go back to pending.
Fixed vs hourly?Fixed may split into 2–3 milestones that must sum to budgetMax. Hourly holds budgetMax as a cap; approved hours cannot exceed remaining escrow.
How is chat authorised?HTTP messages and socket conversation:join both check that the user is a participant. Join is not an open room id.
What is tested?16 API tests on a throwaway Mongo database, Vitest for INR/pricing/relative dates, Playwright smoke for the hire loop, GitHub Actions on main.
What would you do next if this shipped?Rotate JWT_SECRET, turn off SKIP_EMAIL_VERIFY, put files on S3, turn on Stripe, put Socket.IO on Redis if you run more than one API process.
Demo sentence. “Priya hired Aisha on a two-slice inventory app. Scan MVP is already submitted. I will release that slice, leave Offline sync held, and show that one Payment row tracks both amounts.”
