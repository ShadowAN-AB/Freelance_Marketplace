1. What this project is

FreelanceHub is a full-stack marketplace where clients post paid projects and freelancers bid with a single proposal. After a hire, the two parties chat, the freelancer submits work (optionally with files), the client can request revisions or approve, and simulated escrow is released. Both sides can then leave a review. An admin account can inspect users, projects, reports, and analytics.

The product is a classic MERN app (MongoDB, Express, React, Node.js), not microservices. Payments are simulated: accepting a proposal creates a Payment in status held; completing the contract flips it to released. There is no Stripe, email, or LLM matching.

One-line summary. Post → propose → hire (escrow hold) → chat → submit work → optional revision → complete → review.

2. Goals and non-goals

In scope

  • Email/password auth with JWT and bcrypt
  • Project posting, browse, filters, skill matching
  • One proposal per freelancer per project
  • Hire, contract, simulated escrow
  • Deliverable uploads and revision requests
  • Project-scoped chat with presence and unread badges
  • Saved items, proposal shortlists, reports
  • Reviews after completion
  • Admin analytics, block users, moderate reports

Out of scope

  • Real card payments / Stripe / payouts
  • Transactional email or SMS
  • Google / social login
  • LLM-based matching or cover-letter help
  • Milestones or partial releases
  • Mobile native apps
  • Multi-region deployment

4. System architecture

The browser never talks to MongoDB. It talks to Express over HTTP (JSON and multipart) and to the same Node process over WebSockets. JWT is sent as Authorization: Bearer for REST and as Socket.IO handshake auth.token.

AuthContext loads /api/auth/me from localStorage.fh_token, then opens a Socket.IO connection. If the token is missing or rejected, the user is treated as logged out.

8. Core hiring loop

This is the only money path in the product. Everything else (saved items, shortlists, reports, presence) sits on top of it.

Domain rules (enforced on the server)

  • One proposal per freelancer per project (unique index).
  • You cannot bid on your own project or on a non-open project.
  • Accepting a bid rejects other pending bids, sets the project to in_progress, creates a contract and a held payment, and opens (or reuses) a conversation.
  • Chat is allowed only if a pending or accepted proposal exists between the two users on that project.
  • Only the hired freelancer can submit work. Only the client can request a revision or complete.
  • Revision keeps status active, increments revisionCount, stores revisionNote, and clears workSubmittedAt.
  • Reviews are allowed only after completed, once per reviewer per contract. Average rating is recomputed on the reviewee.

9. Feature catalogue

9.1 Auth and profiles

Register is limited to freelancer or client. Passwords are hashed with bcrypt (cost 12). Login is rate-limited (40 attempts / 15 minutes). Blocked users cannot sign in. Profiles store bio, location, avatar, freelancer skills/rate/portfolio/availability, or client company name. PATCH /api/auth/password checks the current password before hashing a new one.

9.2 Projects and skill matching

Clients create projects with category, skills, INR budget range, and deadline. Public browse defaults to open and supports text search, skill, category, and budget filters. Matching score is overlap of required skills plus a small bonus for extra freelancer skills, capped at 100%. Freelancers see recommended open projects on the dashboard; clients see ranked talent on the proposals page.

9.3 Proposals and shortlist

A proposal has cover letter, bid amount, and estimated days. Clients can star pending proposals (shortlisted). The inbox sorts shortlisted first, then newest.

9.4 Work, deliverables, revisions

Submit-work is multipart. Allowed files: PDF, ZIP, PNG, JPEG, WebP, max 8 MB each (up to 8 files). URLs are stored on the contract as deliverables[] and served from /uploads. Re-submit after a revision replaces the list. The client downloads files from the work card, next to Approve and Request revision.

9.5 Saved items

Freelancers bookmark projects; clients bookmark talent. Toggles live on public detail pages. /app/saved lists the populated documents.

9.6 Messaging, unread, presence

Messages persist in MongoDB. Each message has readBy. Unread count is the number of threads whose latest message is not read by the current user. Opening a thread calls POST /conversations/:id/read. Socket.IO maintains onlineUsers and emits presence:update; the chat list shows a teal dot when the other participant is connected.

9.7 Notifications

In-app notifications are created for proposal received/accepted/rejected, messages, work submitted, revision requested, contract completed, review received, and report updates. The shell shows a coral count on Alerts.

9.8 Reports and admin

Signed-in users can report a user or a project with a reason. Admins list reports and set status to reviewed or dismissed, which notifies the reporter. Admins can also block users. Analytics aggregate counts by user role, project status, proposal status, contract status, payment status, and reports.

13. Security and validation

  • Passwords stored with bcrypt; never returned on user documents (select: false).
  • JWT payload is { id, role }. Middleware reloads the user and rejects blocked accounts.
  • Zod schemas on mutating routes. Multer rejects disallowed MIME types.
  • Helmet with cross-origin resource policy so avatars and deliverables can load from the SPA origin.
  • CORS locked to CLIENT_URL. JSON body capped at 1 MB.
  • Auth endpoints rate-limited. Duplicate emails and duplicate proposals return 409.
  • Authorization is checked in controllers (client owns project, freelancer is hired party, conversation participant, and so on). Role middleware is a first gate, not the only gate.
Demo secrets. server/.env ships a development JWT secret. Rotate it before any shared or production deploy. Payments are not real money.

15. Operations notes

  • npm run seed wipes marketplace collections and rebuilds demo users, projects, proposals, contracts, payments, a chat transcript, reviews, and notifications.
  • Uploaded files live on disk under server/uploads/. They are not in Git.
  • Presence is in-memory: a process restart marks everyone offline until they reconnect.
  • If port 27017 already has a local MongoDB, Docker’s mapped port will fail or you will see an empty database. Point MONGO_URI at the instance that actually contains the seed.
  • Vite 6 is pinned because newer Vite/Rolldown builds failed on this machine’s native bindings.
